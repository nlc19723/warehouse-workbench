# 仓库工作台「全局代码审查」标准（常设）

> **版本**：v228.88 ｜ **修订日期**：2026-09-21 ｜ **状态**：已生效，作为后续每次全局审查的统一标准
> **上一版**：v175（2026-08-26，六支柱版）
> **本次修订动因**：v175→v228.87 期间发生 10 起真实事故，旧标准的六支柱**仅捕获 1 起、半捕获 1 起**。真实事故集中在「运行时时序 / 跨端覆盖 / 缓存一致性 / 测试可信度」四类动态面上，而旧标准是纯静态读码框架，结构性失焦。
>
> **一句话定位**：本标准的目的是**在问题造成损失之前拦住它**，而不是在事后写一份漂亮的报告。因此所有条款以「可判定、可复跑、可拒绝发布」为准则。

## 0. 审查原则（v228.88 修订）

1. **不凭感觉列问题**：每条 🔴/🟡 必须附**复现步骤 + 分级证据**（见 §4）。证据强度不足的问题，只能列为「观察项」，不得占用 🔴/🟡 编号。
2. **既报问题也报基线**：除问题清单外，输出「已验证通过（绿灯）」清单。
3. **Gate 必须是拒绝条件**：每条 Gate 必须是**可判真假的布尔条件**。「列明风险点」「评估影响」这类表述**不是 Gate**，无条件通过等于没有 Gate。
4. **数字必须现场生成**：标准正文、报告、Gate 命令中**禁止出现硬编码的规模数字**（文件数、行数、版本号）。一律由 `tools/audit-inventory.mjs` 现场产出。历史教训：v175 标准里写着「26 个 js 文件」「`?v=175`」，到 v228 时全部失真，Gate 命令照抄即失效。
5. **审计脚本入 `tools/`，不落 `/tmp`**（v228.88 修正路径）。历史教训：旧标准写 `scripts/`，而实际工具全在 `tools/`，导致「按标准执行」会拿到能力落后 6 个维度的僵尸扫描器。
6. **修复者不得兼任验证者**：修复完成后的验证必须由**未参与修复的独立脚本**执行，且**断言必须在修复前写死**（防事后调整标准）。历史教训：v228.87 的三缺陷能挖出来，靠的是外部反复追问「是否真的修复了」，而非自证。
7. **债务只减不增**：每轮审查输出债务趋势表（§6），任一指标恶化 >20% 判定为「技术债赤字」，必须附整改计划才允许发布。
8. **标准自身必须可执行**：每轮审查前先跑 §11「标准自检」。自检不通过 → 先修标准，再审代码。

## 1. 审查范围与深度声明

| 项 | 内容 |
|---|---|
| **代码文件** | `js/*.js`（含 `js/components/`）、`css/style.css`、`index.html` |
| **运行时契约文件** | `index.html`（`?v=` 参数）、`service-worker.js`（`CACHE_NAME`）、`manifest.json`、`releases/app-manifest.json` —— **这四项不得跳过** |
| **数据层** | `js/db.js`、`js/data-loader.js`、`js/sync.js`（Dexie + Supabase） |
| **测试基础设施** | `tools/*.py`、`tools/*.mjs`（本身也是被审对象，见支柱九） |
| **深度** | **全面审计**（非抽样）；按风险面分级投入精力 |
| **测试数据** | 真实 Dexie 数据 + 受控 mock 注入 + Playwright 驱动 |
| **跳过项（白名单制）** | 仅 `lib/*.min.js`（第三方压缩产物，只审**调用方式**）。**其余一律不跳过** |
| **视口** | 桌面（1280×800）+ 移动（iPhone 12 / 390×844 / isMobile / hasTouch） |

> ⚠️ **v228.88 修正**：旧版写「跳过构建产物」——本仓是**纯静态 PWA，无构建步骤**，`index.html` + `js/*.js` 即生产产物，该表述等于「跳过一切」。改为白名单制。

## 3. 审查框架：九支柱

> v228.88 由六支柱扩展为九支柱。**原六支柱全部保留**（它们没错，只是不够）；新增七、八、九三支柱覆盖动态面。

### 支柱一 · 逻辑 Bug 与潜在缺陷（继承 + 细化）

- **模块间数据流转**：数据传了没接收 / 接收了没处理（`App.go` / `openEntity` 参数透传、`TableUtils` 与业务模块回调）。
- **条件判断遗漏**：只处理「是」没处理「否」、空/undefined 分支、`??` 与 `||` 混用导致的意外短路。
- **异步时序**：数据未加载完就执行下一步；**Promise 无 catch 静默失败**；同步未完成时 UI 显示陈旧数据；快速切换模块的竞态覆盖。
  - 🔴 **启动引导竞态（事故 #9）**：启动垫底流程（如 `clearWorkTables`）与用户并发导入/同步的先后关系，必须有幂等保护或显式互斥。
- **循环 / 递归**：死循环、闭包持有大对象导致的内存泄漏。
- **事件绑定与泄漏**：重复绑定导致重复提交；模块重渲染后旧监听器未解绑；`document`/`window` 级监听在 SPA 路由切换时未清理；**定时器未随 `disconnect` 清理**。
- **边界情况**：空数据、超长文本、特殊字符、网络断开、移动端/浏览器特定（iOS `<input>` 字号 <16px 强制缩放、`interactive-widget`、`visualViewport` 键盘重定位、触摸 vs 鼠标）、多标签页/多用户并发、空库首次打开、数据量极大。

### 支柱二 · 安全（继承）

本仓涉及合同金额、供应商、库存等敏感数据，且有云端同步 + 本地库 + Excel 导入。

- **XSS（最高优先）**：模板字符串 `${}` 直拼 `innerHTML` 是否全部转义。
  - ⚠️ **转义助手必须收敛（v228.88 新增）**：现状存在 4 个助手（`esc` / `escAttr` / `escapeHtml` / `escapeAttr`），且 `window.escAttr = window.esc` 是**纯别名**——对属性值的转义强度与文本相同，**存在属性注入风险**。
  - 要求：① 收敛为 `esc`（文本）+ `escAttr`（属性，须处理引号/反引号）；② `escapeHtml`/`escapeAttr` 评估统一或标注来源；③ 新增 `innerHTML` 插值必须有对应转义助手，由 CI grep 门禁拦截。
- **导入安全**：Excel 畸形 / 超大文件 / 公式注入（`=HYPERLINK(...)`）的处理。
- **同步与凭证**：Supabase token 存储位置与时效；鉴权失败是否安全降级；敏感数据明文落地 IndexedDB 是否可接受。
  - 🔴 **配置下发防篡改（事故 #3）**：云端下发的连接配置必须**签名校验**后才可跟随；`anon` 可写的键不得直接驱动设备切桶。
- **原型污染**：`Object.assign` / 扩展运算符合并不可信对象（导入数据）时的污染风险。

### 支柱三 · 数据完整性与持久化（继承）

- **Dexie 事务性**：写操作是否原子；页面中途刷新/关闭是否留「半截数据」。
- **同步冲突**：Supabase 多端并发写入的冲突策略（最后写入覆盖？有无版本向量/时间戳）。
- **金额精度**：`parseFloat` / `toFixed` / `*100` / `/100` 浮点运算是否存在漂移；建议整数分或 decimal 库。
- **口径一致性**：自然年 vs 任意区间；各模块金额/数量汇总口径是否统一。
- **删除语义**：删除是否需要**墓碑机制**防跨端复活。

### 支柱四 · 性能与大规模数据（继承）

- **全量加载**：`db.xxx.toArray()` 在 10 万+ 行下的内存与渲染成本。
- **算法复杂度**：按供应商聚合 + 逐行过滤的 `O(n²)` 嵌套循环。
- **渲染**：大列表是否虚拟滚动；全表 re-render 成本。
- **主线程阻塞**：大 Excel 解析是否放到 Web Worker。

### 支柱五 · 流量与配额（🟡 v228.88 大幅强化）

> 旧标准**完全没有流量维度**。但实际约束是 Supabase 免费额度 5GB Cached Egress，且 5s 轮询 × 23 台设备即触顶——这是 v228.83 整个改造的起因。

- **新增轮询必须「搭车」**：任何新增的周期性请求，必须说明复用了哪条既有心跳，**禁止新增独立轮询**。
- **空闲流量门禁**：

  | 指标 | 门禁 |
  |---|---|
  | 空闲 30s 内权限相关请求数 | **必须 = 0** |
  | 变更传播延迟（有人在看时） | **≤ 1.5s**（盘点心跳期）/ 秒级（注意力拉取） |
  | 单设备月度出口估算 | 必须在报告中给出数值 |
  | 新增云端键 | 必须评估其对 `list()` 响应体积的影响 |

- **测量方式**：桩侧访问日志口径（`tools/measure_perm_traffic.py` 已验证可行）。**不接受估算代替实测。**
- **云端目录卫生（事故 #2）**：`list('settings')` 的响应体积直接受文件数影响。测试垃圾文件（`__*`、`b.json`、`d.json`、`work_v*.json` 等）必须清理，且不得再产生。

### 支柱六 · 代码质量与可维护性（继承 + 新增移动端硬指标）

- 全局变量是否过多 / 命名冲突隐患。
- 超长函数是否需要拆分。
- 硬编码值是否应提取为常量 / 配置。
- 🔴 **移动端可触摸性（v228.88 新增硬指标）**：所有可点元素 `getBoundingClientRect().height` **≥ 44px**。仓库场景存在戴手套、急操作，误触成本高，可自动化检测，纳入 Gate。

### 支柱七 · 运行时时序与状态机（🔴 v228.88 新增 · 最高优先级）

> **这是覆盖真实事故最多的一根支柱**（事故 #4/5/6）。旧标准的静态读码根本看不见 `_bustUntil` 恒假、看不见 CDN 返回旧值。**本支柱的条款必须动态验证，不接受仅代码追踪。**

- **§2.7.1 守卫条件可达性**：列出所有 `typeof X !== 'undefined'` / 依赖未初始化变量的守卫。
  - 反例：`if (typeof SyncManager._bustUntil !== 'undefined') X = ...` —— 若该字段从未初始化则**恒假**，赋值永不执行。
  - 要求：可变状态在类字段/模块顶层**显式初始化**（`_bustUntil: 0`），而非依赖 `typeof`。
  - **验收**：构造「变量未初始化」的路径，实测该分支**可达**。
- **§2.7.2 缓存短路的绕过路径**：读缓存前是否检查「本轮必须拿最新值」的标志位？
  - 要求：存在「写入后必须立刻读到新值」的场景时，必须有 `bustActive` 类机制跳过缓存短路。
  - **验收**：统计 busted 直读次数，要求 **> 0**（对照实验）。
- **§2.7.3 拉取-应用链路的完整性**：探测到变更 → 拉取 → 应用 → 重渲，**每一环都要有独立证据**。
  - 反例：探测层修好了，但重渲被 DOM 重绘冲掉（`data-editor-name` 丢失 → `htmlChanged: false` → 静默跳过）。
  - **验收**：端到端断言「变更后 UI 实际变化」+ 时间戳。
- **§2.7.4 存储层陈旧窗口**：写入后多久能读到新值？
  - 实测结论：Supabase Storage CDN 陈旧 **3~10s**，必须用 `?t=时间戳` 绕过。
  - 要求：任何「写完立即读」的路径必须走 cache-buster；非轮询路径（启动/手动刷新）可继续吃 CDN 加速。
- **§2.7.5 轮询读取新鲜度**：缓存 TTL 是否跨轮存活？
  - 要求：采用「时间 + 轮次」双判据（同轮内允许命中，轮次一变立即失效），不依赖时间精度。
- **§2.7.6 定时器生命周期**：每个 `setInterval` 是否有对应的 `clearInterval`？挂载/卸载是否成对？

### 支柱八 · 跨端一致性与防覆盖（🔴 v228.88 新增）

> 覆盖事故 #1/#7。这是「数据丢失」类问题的唯一根因支柱。

- **§2.8.1 空值保护**：任何「同步某集合到云端」的路径，**本机为空时绝不上云空值**。
  - 反例：`syncKeepers()` 在本机账号为空时也上传 `[]`，覆盖云端唯一备份 → 所有设备再也拉不回。
  - 要求：写云端前判断「本机是否为空且云端非空」，是则**跳过写入**。
- **§2.8.2 单向 vs 双向（防反向覆盖）**：接收端拉取后**不得回写云端**。
  - 反例：`pullKeepersFromCloud` 合并后调 `setKeepers()`，默认会推本机列表上云；一旦本次读到陈旧值，就用旧列表覆盖管理员刚授予的权限。
  - 要求：拉取路径必须传 `{ pushCloud: false }` 类开关，只落本地。
- **§2.8.3 真相源定义**：每个键必须明确「权威副本在哪」。
  - 反例：`keepers` 的真相源设计为「各设备本机」，但云端备份是唯一的跨设备通道 —— 真相源模糊导致双向覆盖无人负责。
- **§2.8.4 墓碑机制**：删除必须有墓碑，防止「云端独有 → 合并回本地」复活已删项。
- **§2.8.5 写入序列单调性（硬验收）**：从**服务端/桩日志**读取该键的全部写入记录，要求序列**严格符合预期、无回退**。
  - 这是 v228.87 修缺陷②所用的手段，**固化为标准动作**。

### 支柱九 · 测试基础设施可信度（🔴 v228.88 新增）

> 覆盖事故 #2/#8。**这是最容易被忽略、但已多次误导排查方向的一根支柱。** 测试本身不可信时，所有结论都是假的。

- **§2.9.1 版本正确性前置断言**：测试跑起来后，**第一件事**是断言「加载的代码版本 == 目标版本」。
  - 强制项：① `service_workers='block'`（禁止 SW 返回旧缓存）；② URL 的 `?v=` **动态读取** `js/config.js`，**禁止硬编码**；③ 断言关键文件的 hash/特征串。
  - 反例：e2e 硬编码 `?v=228.83` 未随 sed 更新 + SW 的 `CACHE_NAME` 旧值 → 加载旧 JS → 假失败，误导排查 2 小时。
- **§2.9.2 零真实请求断言**：任何走查/模拟/回归脚本，必须**硬拦截**所有出口，并在结束时**断言真实云端请求数 = 0**。
  - 反例：走查只 mock 了 `SyncManager` 通道，而 `db.js` 的任务同步走**独立 Supabase client** 漏了拦截 → 41 条假任务写进**生产桶**。
  - 要求：拦截层必须是「网络层」（如 Playwright route 拦截），而非「调用层」。
- **§2.9.3 桩的可观测性**：测试桩必须记录**请求方法 / 路径 / 响应内容**，供事后审计（这是写入序列单调性验收的数据源）。
- **§2.9.4 脚本落盘位置**：一律 `tools/`，禁止 `/tmp`。脚本须自带 `usage` 注释与产出说明。
- **§2.9.5 对照实验**：关键修复必须提供「改前 vs 改后」的量化差异（如 busted 直读 0 次 → 17 次）。
- **§2.9.6 验证者独立性**：见 §0.6。

## 4. 证据分级（🔴 v228.88 新增）

> 旧标准把「Playwright 截图 / 控制台日志 / 代码追踪（行号）」**并列**为证据。但三者强度差异极大——**代码追踪只证明代码在位，不证明它跑了**。

| 级别 | 证据类型 | 能证明什么 | 可用于 |
|---|---|---|---|
| ⭐ | 代码追踪（行号） | 代码在位 | 仅限参考 |
| ⭐⭐ | Playwright 截图 | 某时刻的渲染结果（可能是旧缓存） | 🟢 优化项 |
| ⭐⭐⭐ | 控制台日志 | 代码执行过（可能被吞） | 🟡 中等问题 |
| ⭐⭐⭐⭐ | Playwright 断言 + 时间戳 | 行为发生且可量化 | 🟡/🔴 |

## 10. 发布后验证与回滚预案（🔴 v228.88 新增）

### 回滚预案（必须预先定义）

| 情况 | 动作 |
|---|---|

### 数据安全

- 发布前对云端关键键（`keepers`、`cloudConfig`、`outbound_list`、主数据包）做**导出快照**。
- 快照产物路径：`/workspace/cloud_backup/<日期>/`。
