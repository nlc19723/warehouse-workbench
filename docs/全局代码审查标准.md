# 仓库工作台「全局代码审查」标准（常设）

> 制定日期：2026-08-26 ｜ 状态：已生效，作为后续每次全局审查的**统一标准**
> 目标：在原有三支柱规范基础上，扩成六支柱 + 三项交付硬要求，形成一份**可复现、可验证、带证据**的全局审查标准。
> 适用范围：每次全量审计（如 v175 及以后各版本）均依此标准执行；各版本发现与结论记入对应的 `全局代码审查报告_vXXX.md`。

---

## 0. 审查原则

1. **不凭感觉列问题**：每条 🔴/🟡 必须附复现步骤 + 实测证据（Playwright 截图 / 控制台日志）或精确代码追踪。
2. **既报问题也报基线**：除问题清单外，输出「已验证通过（绿灯）」清单，让用户知道健康基线。
3. **自动化 gate 前置**：全量 `node --check` + Playwright 双视口冒烟 0 error 为发布门槛。
4. **版本一致性专项**：`index.html` / `js/config.js` / `releases/app-manifest.json` 三处版本号同步，列为固定检查项（历史反复踩坑）。
5. **审计脚本入库**：验证/扫描脚本写入 `scripts/`，不落 `/tmp`，保证可复跑。

## 2. 审查框架：六支柱

### 支柱一 · 逻辑 Bug 与潜在缺陷（继承 + 细化）
逐项检查（覆盖你原规范的 6 点，并细化）：

- **模块间数据流转**：数据传了没接收 / 接收了没处理（如 `App.go` / `openEntity` 参数透传、`TableUtils` 与业务模块回调）。
- **条件判断遗漏**：只处理「是」没处理「否」、空/undefined 分支、`??` 与 `||` 混用导致的意外短路。
- **异步时序**：数据未加载完就执行下一步；**Promise 无 catch 静默失败**（全仓 88 处 `await` 无 `catch`）；同步未完成时 UI 显示陈旧数据；快速切换模块的竞态覆盖。
- **循环 / 递归**：死循环、闭包持有大对象导致的内存泄漏。
- **事件绑定与泄漏**：重复绑定导致重复提交；**模块重渲染后旧监听器未解绑**；`document`/`window` 级监听在 SPA 路由切换时未清理（即此前全局审查第五节关注点）。
- **边界情况**：空数据、超长文本、特殊字符、网络断开、**移动端/浏览器特定**（iOS `<input>` 字号 <16px 强制缩放、`interactive-widget`、`visualViewport` 键盘重定位、触摸 vs 鼠标事件）、**多标签页/多用户并发**、**空库首次打开**、**数据量极大**。

### 支柱二 · 安全（新增 ⚠️）
本仓涉及合同金额、供应商、库存等敏感数据，且有云端同步 + 本地库 + Excel 导入，安全不可缺：

- **XSS（最高优先）**：模板字符串 `${}` 直拼 `innerHTML` 是否全部转义。
  - 已定义 `window.esc`（`config.js:65`），但覆盖不均：**`stock.js`/`query.js`/`low-turnover.js` 的 `innerHTML` 次数 > `esc()` 次数**，存在未转义注入嫌疑 → 重点核查。
  - 导入的供应商名/存货名含 `<script>` 等是否会被执行。
- **导入安全**：Excel 畸形 / 超大文件 / 公式注入（如 `=HYPERLINK(...)`）的处理。
- **同步与凭证**：Supabase token 存储位置与时效；鉴权失败是否安全降级；敏感数据（合同金额）明文落地 IndexedDB 是否可接受。
- **原型污染**：`Object.assign` / 扩展运算符合并不可信对象（导入数据）时的污染风险。

### 支柱三 · 数据完整性与持久化（新增）
- **Dexie 事务性**：写操作是否原子；页面中途刷新/关闭是否留「半截数据」。
- **同步冲突**：Supabase 多端并发写入的冲突策略（最后写入覆盖？有无版本向量 / 时间戳）。
- **金额精度**：全仓 **90 处** `parseFloat` / `toFixed` / `*100` / `/100` 浮点运算是否存在漂移（如 `0.1+0.2` 类）；建议整数分或 decimal 库。
- **口径一致性**：自然年 vs 任意区间（v175 占比已暴露此问题）；各模块金额/数量汇总口径是否统一。

### 支柱四 · 性能与大规模数据（新增）
- **全量加载**：全仓 **10+ 处** `db.xxx.toArray()`（集中在 `data-loader.js`/`db.js`），在 10 万+ 行下的内存与渲染成本。
- **算法复杂度**：按供应商聚合 + 逐行过滤的 `O(n²)` 嵌套循环。
- **渲染**：大列表是否虚拟滚动；全表 re-render 成本。
- **主线程阻塞**：大 Excel 解析是否放到 Web Worker，避免卡死 UI。

### 支柱五 · 无用代码清理（继承）
- 已废弃未删的函数 / 变量 / 样式。
- 注释掉的大段代码（临时注释需标注、废弃需删除）。
- 引入但未使用的第三方库 / 插件。
- 重复定义的逻辑（两处几乎一样的实现）。

### 支柱六 · 代码质量与可维护性（继承）
- 全局变量是否过多 / 命名冲突隐患（`App`、`db` 为顶层 `const`）。
- 超长函数是否需要拆分（如 `render` / `applyFilter` / 聚合函数）。
- 硬编码值（写死数字、路径、文本）是否应提取为常量 / 配置（如 `kpiAllLimit` 真实用途核查）。

## 3. 严重度与影响面定义

| 级别 | 定义 | 处置 |
|---|---|---|
| 🔴 严重 | 功能异常 / 数据丢失 / 页面崩溃 / 安全漏洞 | 必须立即修复 |
| 🟡 中等 | 功能可用但有隐患 / 交互体验差 | 建议尽快处理 |
| 🟢 优化 | 规范 / 冗余清理类 | 可排期 |

**每条问题附加**：`触发频率 × 影响半径`（likelihood × blast radius），用于排序。

## 6. 执行阶段（分阶段，每阶段有产出）

- **Phase 1 · 静态盘点**：生成文件清单、依赖清单、全局变量清单、内联 `innerHTML` 清单、`await` 无 `catch` 清单、`toArray` 清单、浮点运算清单 → 输出 `scripts/audit-inventory.json`。
- **Phase 2 · 六支柱核查**：逐项人工 + 工具核查，产出原始发现表。
- **Phase 3 · 实测验证**：对 🔴/🟡 用 Playwright 复现并取证（截图 / 日志）。
- **Phase 4 · 报告汇总**：问题分级清单 + 绿灯基线 + 版本一致性 gate 结论 → `全局代码审查报告_v175.md`。
- **Phase 5 · 评审与排序**：按 `severity × 频率` 给出修复建议顺序（用户最终决定）。

## 9. 范围与深度声明（避免误判「全覆盖」）

- 本方案为**全面审计**，但对「安全 / 精度 / 性能」三类（此前规范缺失）投入更高权重。
- 跳过项见 §1（第三方库内部、构建产物、`.git`）。
- 审计不修改任何业务代码；发现问题仅出报告与修复建议，修改由后续单独任务执行。
