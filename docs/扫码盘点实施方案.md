# 扫码盘点 · 实施方案 v4（各自认领模式 + 独立扫码定位）

> 基线 v214。**v4 相对 v3 的两项调整**：① 分配改为**各自认领**（自填名字 + 自选序号区间 + 隐藏未选行 + 本地自动缓存），去掉"固化进批次/管理员分派/区间校验"；② 扫码**独立按钮**（不在过程页），识别后**定位到盘点表格对应行**而非跳档案。

## 一、分配方案为什么换成"各自认领"

| | v3 管理员分派（已弃） | v4 各自认领（采用） |
|---|---|---|
| 谁分 | 管理员统一分派到账号 | **各人自己填名字、自己选序号区间** |
| 依赖 | 必须先把"登录账号/库管员账号"做好才能分给人 | **不依赖登录态**，现在就能做 |
| 数据 | 要把全库 `items` 固化进批次 + `assignments` + 均分算法 + 重叠校验 | 只存"我选了哪段、我叫什么"，极轻 |
| 复杂度 | 高（你说"太麻烦"，确实） | 低 |

> **关键**：等登录态（D 角色模型）完善后，只需把"自己填名字"改成"自动带出当前登录账号"，**其余逻辑一行不用改**。

## 二、序号：不固化，但要"锁定排序"（唯一前提）

不固化进数据库可以，但必须保证**序号 = 表格行号**在盘点期间不漂移，否则"我选 1-45"下次打开就变了。

**做法（不存库，靠界面锁定）**：

| 措施 | 说明 |
|---|---|
| 进入盘点态后**禁用列排序** | `TableUtils.initSortableHeaders` 在盘点态不挂载（或挂了也置灰），避免点表头重排导致序号变 |
| 盘点态**不分页 / 全量渲染** | 序号按全量 1..N 连续，不受分页影响 |
| 行顺序固定 | 按 `存货编码` 升序渲染（`stock` 表有该索引），每次进模块顺序一致 |
| 序号 = 渲染行号 | 第 1 行就是 1 号，所见即所得，和你截图语义一致 |

> 这样"不固化"也能得到稳定序号；代价是盘点态不能排序/分页——对盘点场景反而更顺手。

## 三、盘点模块完整流程（v4）

### 3.1 顶部结构

```
[ 开始日期 ] 至 [ 结束日期 ]   [ 日常盘点 ]  [ 季度盘点 ]
[ 盘点人：____ ] [ 序号：__ 至 __ ] [ 开始盘点 ]      ← 选完区间点这里
[ 📷 扫码 ]  [ 💾 保存盘点 ]  [ 🏁 盘点结束 ]  [ 🗑 清空草稿 ]
```

- **扫码是独立常驻按钮**（见第五节）；
- 点【日常/季度盘点】→ 按规则渲染行（见 3.2 / 3.3）；
- 填【盘点人】+【序号 起始-结束】→ 点【开始盘点】→ **只显示该区间内的行，其余隐藏**。

### 3.2 日常盘点（筛选逻辑沿用 v3 纠正版）

```
getOutbound(区间) 汇总 → 得到"出过库的编码集合 S"
   ↓
从 getStock() 全库中只保留 编码 ∈ S 的行（其余隐藏）
   ↓
对保留行：getInbound(区间) 汇总 → 填【入库量】列（仅参考，可为 0）
   ↓
露出【出库量】【入库量】两列 + 【💾 保存盘点】
```

> 筛选**只用出库**；差异量 = 盘点数量 − 现存量（不减出入库量）。

### 3.3 季度盘点

- 不按出/入库筛选，**列出全库物料**；
- 同样露出【出库量】【入库量】两列（按区间汇总填充）；
- 后续与日常一致：填名字 → 选序号区间 → 隐藏未选行 → 录数 → 保存。

### 3.4 选区间后

| 行为 | 说明 |
|---|---|
| 隐藏未选行 | 只渲染 `序号 ∈ [起始, 结束]` 的行，其余隐藏（不删除） |
| **去掉已盘部分** | 再剔除"本人已保存过"的编码（见 12.4），只显示**真正没盘过的** |
| 区间可改 | 改区间 → 重新渲染；已填的数量**不丢**（按存货编码存在草稿里） |
| 进度提示 | 顶部显示 `已盘 30 / 45`（含"本次已存 / 仍待盘"） |
| 重叠 | **允许**（各人选各人的）；保存时若该编码已有别人保存过 → 提示"该行已被 XXX 盘点过"，默认**追加一条**记录（不覆盖），导出时看得到 |

### 3.5 本地自动缓存（未保存也不丢）

| 触发 | 行为 |
|---|---|
| 每填一个【盘点数量】 | **立即**写本地草稿（localStorage），无需点保存 |
| 切换模块 / 刷新 / 关页面 | 草稿仍在 |
| 重新进入盘点模块 | 检测到草稿 → 弹提示：`上次有未完成的盘点（张三 · 序号 1-45 · 已填 30 条），继续还是重新开始？` →【继续】恢复人/区间/数量 |
| 点【保存盘点】 | 写入本地 `stocktake_records` → **追加推送云端第 4 包** → 清除该草稿（详见 12.3） |
| 点【🏁 盘点结束】 | 标记本批次 `closed` 上云 + 清草稿 + 重置输入（详见 12.5） |
| 【🗑 清空草稿】 | 手动丢弃 |

```js
// 草稿结构（localStorage，单键）
stocktake_draft_v1: {
  sheetType:'daily'|'quarter', startDate, endDate,
  counter:'张三', noStart:1, noEnd:45,
  rows: { 'A001': { countedQty:118, ts:ISO }, 'A002': {...} },
  updatedAt: ISO
}
```

## 四、数据模型

```js
// 盘点记录（保存后写入本地 + 推送云端第 4 包；不进 data.json 的 10 表）
stocktake_records: [{
  recId,        // 全局唯一（crypto.randomUUID），追加去重与覆盖的唯一键
  sheetId,      // 批次标识 = `${sheetType}_${startDate}_${endDate}`
  sheetType:    'daily'|'quarter',
  code, name, spec, systemQty,
  periodOutQty, periodInQty,
  countedQty, diff,
  counter,      // 自填名字（登录态完善后可自动带出）
  noStart, noEnd,
  startDate, endDate, countedAt,
  deviceId,     // 本机标识（追溯来源）
  note, voided:0
}]
```

**盘点任务 task**（存云端第 4 包 `tasks` 段，全设备共享）：
```js
tasks: [{
  taskId, sheetId, sheetType,
  counter,        // 归属人
  noStart, noEnd, // 认领的序号区间
  status: 'open'|'closed',   // open=盘完继续；closed=该人该区间已结束（未盘的记 0）
  createdAt, closedAt, deviceId
}]
```
> 任务粒度是 **「人 + 序号区间」**：结束只结束自己那段，与他人无关。

> **去掉** `stocktake_sheets.items` 固化、`assignments` 分派、均分算法、重叠强校验。
> 保留：`stocktake_records` 一张业务表 + 一个 localStorage 草稿键 + 云端第 4 包。

## 五、扫码（独立按钮 · 定位到表格行）

### 5.1 定位与形态

- **独立常驻**在盘点模块顶部（`📷 扫码`），**不在过程页内**、不依赖是否点了日常/季度；
- 是**可选工具**：不用也能纯手填。

### 5.2 行为（识别 → 定位行，而非跳档案）

```
点【📷 扫码】→ QRScan.open('stocktake')
   ↓ 识别到编码 code
在当前盘点表格中查找 code 对应的行
   ├─ 命中且在当前可见区间内 → 滚动到该行 + 高亮闪烁 + 自动聚焦【盘点数量】输入框
   │                          → 填数确认 → 差异量实时重算 → 自动跳下一未盘行
   ├─ 命中但被区间隐藏      → 提示"该编码不在你选的序号区间（当前 1-45）"→ 【取消本次操作】（不填数、不跳行、不改区间）
   └─ 编码不在本表          → Toast"该编码不在盘点范围内"（不跳页、不报错）
```

- 扫码与手填**完全等价**，随时可切；
- 扫码的每次填数**同样自动进本地草稿**；
- 关闭扫码 → 自动恢复普通模式（普通扫码仍跳档案，**行为保持**）。

### 5.3 代码落点

- `js/qr-scan.js`：`open(mode)` 增 `mode:'stocktake'`；盘点模式下 `onDetected` 调 `StocktakeModule.focusRowByCode(code)`（**不再** `App.openEntity('stock', code)`）；
- 非盘点模式分支原样保留。

## 十一、云端同步策略与污染风险评估【实证结论】

> 你担心的"盘点数据会不会污染云端"，答案：**按本方案实现，不会污染，本地记录也不会被云端覆盖清空。**

### 11.1 三个实证依据（已读代码确认）

| # | 代码事实 | 结论 |
|---|---|---|
| 1 | `data-loader.js:26` `TABLES` = 10 张业务表；`pushAllToCloud` 只遍历这 10 张打包推送 | 新增的 `stocktake_records` **不在**推送清单 → **不会推到云端，零污染** |
| 2 | `db.js:184-197` `clearAll()` 是**硬编码 10 张表**逐一 clear（suppliers/orders/inbound/stock/inventoryAlerts/orderChecks/pricing/lowTurnover/breach/outbound） | 云端覆盖本地时，新表**不在清空清单** → **盘点记录不会被误删** |
| 3 | `data-loader.js:31` `REQUIRED_TABLES` = 8 张，`_isBundleComplete` 只校验这 8 张 | 新表不参与完整性校验 → **不会导致同步被拒绝** |

> 结论：**新增一张独立本地表，天然与云同步隔离**，不需要改任何同步逻辑。

### 11.2 Dexie 事务越界排查（已排除）

`loadBundleFromCloud` 的事务范围是 `this.TABLES.concat(['outbound','meta'])`。若新表不在事务范围内又被访问，Dexie 会抛"事务越界"。
**已确认**：事务内只做 `clearAll()`（不碰新表）+ 遍历 `this.TABLES` 还原（不碰新表）→ **全程不访问新表，无越界风险**。

### 11.3 加表方式（升版本，不影响现有数据）

```js
db.version(8).stores({
  stocktake_records: '++id, 存货编码, 盘点人, 盘点日期, 盘点类别'
});
```
> Dexie 升版本**只加表不清数据**，现有 10 张表数据不受影响（当前最新为 `db.version(7)`）。

### 11.4 盘点记录要不要上云？（建议分两步）

| 方案 | 做法 | 优点 | 缺点 | 最终决定 |
|---|---|---|---|---|
| **A 纯本地 + 导出备份** | 记录只存本地 IndexedDB；提供【导出 xlsx / JSON】+【导入恢复】 | 零污染、零改同步逻辑 | 换设备看不到他人记录 | 降级为**离线兜底**（未连云端时） |
| **B 独立通道上云** | 新增**第 4 个数据包 `stocktake.json`**，与 3 个现有包并列；**追加式合并** | 多设备共享、实时、可追加 | 需写 push/pull 与合并逻辑 | ✅ **采用（见第十二节）** |
| **C 塞进 bundle 一起同步** | 把 records 加进 `TABLES` 一起整包推拉 | — | ❌ 整包覆盖：A 推含盘点的 bundle，B 拉下会覆盖本地记录；bundle 变大、同步变慢 | ❌ **不推荐** |

> **关键洞察**：盘点记录是**追加型数据**（每条只增不改），不像 bundle 那样整包覆盖——所以将来上云时，用"独立通道 + 追加合并"是安全的，这也是选 B 而非 C 的原因。

### 11.5 两个真实风险提醒（非污染，但要注意）

| 风险 | 说明 | 对策 |
|---|---|---|
| **盘点中途重新导入数据** | 若盘点期间执行"数据导入/重新导入"，`stock` 表被 clearAll 后重导 → 此前快照的"现存量"与新数据对不上 | 保存时校验：若 `stock` 更新时间晚于盘点开始时间，提示"库存数据已变更，请确认后保存" |
| **本地记录随浏览器清理丢失** | 本地存储，清缓存/换浏览器即失 | 云端第 4 包已解决（可从云端拉回）；【导出备份】仍保留做离线兜底 |

## 十二、第 4 个云端数据包设计（`stocktake.json`）

### 12.1 现有 3 包 vs 新增第 4 包

| # | 文件 | 内容 | 同步模型 | 是否覆盖 |
|---|---|---|---|---|
| 1 | `data.json` | 工作数据（10 张业务表） | 整包 + `savedAt` 乐观锁 | ❌ 覆盖式 |
| 2 | `base.json` | 基准数据（系统底账） | 整包 | ❌ 覆盖式 |
| 3 | `settings.json` | 设置偏好 | 合并式（getSetting/setSetting） | ✅ 合并 |
| 4 | **`stocktake.json`**（新增） | **盘点记录 + 批次状态** | **追加式（recId 去重合并）** | ✅ **追加** |

> **与前两包的本质区别**：`data.json`/`base.json` 是"整包覆盖"，所以多人同推会互相覆盖；`stocktake.json` 是**追加型**——每条记录只增不改（改=作废后新增），天然不会互相覆盖。

### 12.3 追加同步机制（pull → merge → push）

```js
async pushStocktake(newRecords) {
  for (let attempt = 0; attempt < 3; attempt++) {
    const cloud = await SyncManager.pullStocktake();        // ① 拉全量
    const base  = (cloud && cloud.savedAt) || null;
    const map   = new Map();
    (cloud?.records || []).forEach(r => map.set(r.recId, r));
    newRecords.forEach(r => map.set(r.recId, r));           // ② 按 recId 去重（同 id 视为同一条）
    const merged = [...map.values()];
    const res = await SyncManager.pushStocktake(            // ③ 带乐观锁写回
      { savedAt: new Date().toISOString(), tasks: mergedTasks, records: merged },
      base
    );
    if (res === true) return true;
    if (res !== 'conflict') return false;
    // conflict：期间有人先写了 → 重新 pull-merge 再试
  }
  return false;
}
```

| 要点 | 说明 |
|---|---|
| **去重键** | `recId`（`crypto.randomUUID()`），**全局唯一**，不同设备不会撞车 |
| **追加语义** | 新记录 merge 进全量后整体写回；别人的记录**原样保留** |
| **并发** | `savedAt` 乐观锁 + 最多 3 次重试；极端同时写入最坏丢极小部分，不覆盖他人 |
| **失败兜底** | 云端不可用时，记录仍存本地，标记 `pendingSync`，恢复后自动补推（离线兜底） |
| **不污染** | 完全独立文件，`data.json` 的 10 表**一行不动** |

### 12.4 "去掉已保存部分"的过滤逻辑（续盘）

进入盘点模块 → 点日常/季度盘点后：

```
① 拉取云端 stocktake.json 合并到本地（拿到所有人已存的记录 + tasks）
② 计算「应盘全集 S」
    日常盘点：区间内有出库的编码集合
    季度盘点：全库所有编码
③ 计算「本人已盘集合 C」
    C = 盘点记录中 sheetId = 当前批次 且 counter = 当前盘点人 的编码
    （含"盘点结束"时补 0 的那些行 —— 它们也在记录里，所以同样被剔除）
④ 本次显示 = (S ∩ 本人序号区间) − C
```

> **空态提示（已纳入设计）**：当 `S`（日常盘点=有出库的物料集合）为空时，日常盘点表格显示 0 行并提示：
> "当前筛选区间内**无出库记录**。日常盘点以出库为准；如需按全库清点，请使用【季度盘点】。"
> 实测当前云端 `outbound=0`，**上线初期日常盘点必然空表**，此提示避免误判为功能故障。

| 场景 | 效果 |
|---|---|
| **只点【保存】**（盘了 1-20，区间 1-45） | 下次进入显示 **21-45**，继续盘剩下的 ✅ |
| **点了【结束】**（区间 1-45） | 未盘的 21-45 已**记 0 入库**，下次不再出现 ✅ |
| 李四选 46-92 从未盘过 | 显示完整 46-92 |
| 张三结束 1-45 后又改选 1-100 | 1-45 已在记录里（含补 0 的）→ 只显示 46-100 |
| 该 task 已 closed 且又选了同区间 | 提示"该区间你已盘点结束"，可改选区间或新建任务重盘 |

> 因为过滤按 **counter + 区间** 取"本人已盘"，所以各人只去掉自己盘过的，**张三结束 1-45 不影响李四的 46-92**——和"各自认领"模式天然契合。

### 12.5 【💾 保存】vs【🏁 盘点结束】—— 两种操作的区别

> 这是本次最关键的业务规则修正：**"结束"是「个人 + 序号区间」级的，不是批次级的**。

| 操作 | 已填的行 | **未填的行** | 任务状态 | 下次进入 |
|---|---|---|---|---|
| **【💾 保存】** | 写入记录（推云端） | **不写、不补 0**（留着下次盘） | 保持 `open` | **继续盘剩下的** |
| **【🏁 盘点结束】** | 写入记录（推云端） | **按 `盘点数量 = 0` 写入**（差异 = −现存量，即盘亏） | 置 `closed` | 该区间不再出现 |

**为什么未盘的记 0**：盘点要求区间内全覆盖，结束时没盘到即视为"盘没（0）"，差异量 = 0 − 现存量 = 全额盘亏。这是明确的业务语义，也让"结束了多少"可结算。

### 12.5.1 任务（task）数据

```js
// 存云端 stocktake.json 的 tasks 段（全设备共享）
tasks: [{
  taskId: 'uuid',
  sheetId: 'daily_2026-08-01_2026-08-30',
  sheetType: 'daily'|'quarter',
  counter: '张三',           // 任务归属人
  noStart: 1, noEnd: 45,     // 他认领的序号区间
  status: 'open'|'closed',
  createdAt, closedAt, deviceId
}]
```

> 任务按 **counter + 区间** 区分：张三结束自己的 1-45，**不影响**李四的 46-92。

### 12.5.2 【🏁 盘点结束】流程

```
点【🏁 盘点结束】
   ↓
统计：本次区间内 已填 X 条 / 未填 Y 条
   ↓
┌─────────────────────────────────────────────┐
│ 确认结束本次盘点？                            │
│ 区间：序号 1 - 45（张三）                     │
│ 已盘点：30 条                                 │
│ ⚠️ 未盘点：15 条 —— 将按「盘点数量 = 0」计入   │
│    （差异量 = −现存量，记为盘亏）              │
│                        [ 取消 ]  [ 确认结束 ] │
└─────────────────────────────────────────────┘
   ↓ 确认
① 已填行 → 写记录；未填行 → countedQty=0 写记录
② 全部追加推云端第 4 包
③ 该 task 置 closed（上云）
④ 清除本地草稿；提示"张三 · 1-45 盘点已结束（30 实盘 + 15 记 0）"
```

| 项 | 设计 |
|---|---|
| **权限** | ✅ **任何人可点**（结束的是他自己的区间，不影响他人） |
| **防误触** | 二次确认弹窗**必须显示未盘条数**，避免随手一点把几十条记成 0 |
| **结束后** | 该任务区间不再出现在他的待盘列表；他人区间不受影响 |
| **重开** | 结束后若需重盘该区间 → 改选区间会创建新 task（旧记录保留，导出可见） |
| **历史** | 记录永久保留在盘点记录模块，记 0 的行可被筛选/导出查看 |

| 时机 | 动作 |

**⚠️ 重要发现 — 出库为空时日常盘点会空表：**
当前 `outbound=0`，而日常盘点规则是"仅保留区间内有出库的物料"。**这意味着上线初期（出库数据为空）点【日常盘点】会显示 0 行**——这是 P4 规则的正确结果，但容易让人误以为功能坏了。

> **对策（已纳入实施）：** 日常盘点结果为空时，显示明确空态提示：
> "当前筛选区间内**无出库记录**。日常盘点以出库为准；如需按全库清点，请使用【季度盘点】。"
> 待你后续录入出库单后，日常盘点自动有数据。

**P5 性能定论：** 1407 行全量渲染无压力；入库 24405 行聚合，在升 version 8（Step 1）时**把 `入库日期` 加进 inbound 索引、`出库时间` 加进 outbound 索引**，改用 `.where('入库日期').between()` 索引查询，即使数据翻倍到 5 万+ 仍稳定（实测全扫 24405 行 <100ms，加索引后更稳）。
